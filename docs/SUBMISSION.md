# Submission walkthrough

**Working experience:** https://oauthpath-drab.vercel.app

**Source repository:** https://github.com/9059Rohith/oauthpath

## The problem and the scope

A provider OAuth app is the identity and configuration that users authorize. It is separate from the developer's integration and from each user's connection and tokens. Sometimes a managed app removes the need to create a registration; otherwise provider requirements can delay legitimate external access. The product starts with that ownership decision, then gives developers a concrete next action.

This slice uses eight real providers rather than manufacturing a hundred shallow pages. GitHub exposes app-model choices; Google/Gmail exposes scope-dependent verification; Slack separates distribution routes; LinkedIn exposes gated access. Notion, Zoom, Shopify and Atlassian add different app and distribution models. The same content model supports a larger library. Live research covers apps outside it.

## A five-minute review

1. Open **Start here**. Select managed ownership, inspect the official directory link, then switch to custom. Availability remains provider/method-specific rather than being guessed.
2. Open GitHub, then Google/Gmail. Compare the stated scenario, hands-on planning estimate, waiting, approval route, source-backed requirements and human handoffs.
3. Check one task. The next-action card advances. Reload, continue, and open the target disclosure. Copy the handoff or export Markdown; sources travel with the guide.
4. Open live research. Submit an unfamiliar provider or its public documentation URL. Optionally select a pilot/internal/public audience and describe a capability. The activity log shows actual discovery, retrieval, synthesis, verification and save events.
5. Open the completed guide and share its permanent URL. Inspect its research mode, actual HTTP observations, evidence and uncertainties. Failed research offers an explicit retry state and publishes no draft.

## What the investigation changed

- Google originally skipped client creation and callback handling. The guide now separates credentials, audience eligibility, callback security, token exchange and a scoped read-only test.
- GitHub's alternative app models originally blurred together. The guide now explicitly follows OAuth App setup and links to the different GitHub App route.
- Dropbox's two-week threshold deadline is not an approval-turnaround promise. Production limits and freeze recovery are source-conditioned.
- Linear public distribution is relevant to external workspaces, not an automatic prerequisite for an internal-only app.
- An initial Miro draft confused external sharing with Marketplace publishing. Independent source review found its installation-link route. The unpublished local draft prompted a separate launch-policy search, stronger route distinctions, and maintained sharing-document entry points.
- Miro's embedded Web SDK App URL setting also appeared in a REST-only draft. Its official manifest reference establishes that `sdkUri` is Web SDK only; the revised research path keeps the REST callback in `redirectUris` and makes embedded UI configuration conditional.
- Document fetch success establishes retrieval only. Failed source requests, unavailable facts, account sign-in and provider review remain separate evidence states.

## Deliberate limits

This is a working take-home slice, not a claim of universal correctness or completed provider approvals. No paid provider accounts or end-user OAuth credentials are required. Account-bound authentication, consent, legal commitments and submission remain human actions. The system does not autonomously register provider apps. See the README and evaluation for measured performance and operational limits.
